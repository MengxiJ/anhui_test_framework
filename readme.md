# 安汇智投平台 · 自动化测试框架（T-Blocks）

> 面向真实 P2P 金融平台的自动化测试项目：第一代采用传统 PageObject 方式实现 169 个用例；
> 在此基础上自研「积木式」框架 **T-Blocks**，将新增用例的成本从「编写代码」降为「拼装 JSON」。

## 项目背景

测试对象为**安汇智投平台**——一个在线 P2P 借贷网站，包含前台（注册、登录、开户、充值、投标、发标）
与后台（管理员登录、额度审核、标的初审、满标复审、借款列表管理）。本项目为其搭建了完整的自动化测试体系，
覆盖接口、UI、端到端流程、性能与安全。

项目的核心价值在于**框架本身的演进**：

- **第一代（`old_framework/`）**：经典 PageObject + pytest 参数化，169 个用例。
  功能可用，但每新增一条用例都需编写 Python，断言与流程耦合，维护成本随用例规模持续上升。
- **第二代（根目录，T-Blocks）**：自研积木式框架。将业务动作封装为 194 个原子节点
  （117 个步骤 + 77 个检查），用例即一个 JSON 文件，通过节点与连线完成编排。
  **新增边界用例只需在 JSON 中增加一行数据，无需编写任何代码。**

## 从第一代到第二代

| <br />  | 第一代 PageObject   | 第二代 T-Blocks                |
| ------- | ---------------- | --------------------------- |
| 编写一条用例  | 编写一个 Python 测试函数 | 拼装一个 JSON 文件                |
| 新增边界用例  | 复制代码并修改参数        | 在 JSON 中增加一行 `data_rows` 数据 |
| 断言      | 固化在用例内部          | 独立的检查节点，跨用例复用               |
| 复用粒度    | 页面对象 / 方法        | 194 个原子节点自由组合               |
| 错误暴露时机  | 运行中才失败           | 运行前静态检查即拦截                  |
| 性能 / 安全 | 依赖外部工具（JMeter 等） | 框架内置压测引擎与安全基线用例             |

> 用例数由 169 变为 91，覆盖面反而更广：大量重复的参数化脚本由 5 个数据驱动文件（41 行数据）替代，
> 同时新增性能压测、并发测试、安全基线、数据驱动边界测试，以及覆盖前后台双站点的完整业务链
> （发标 → 初审 → 投标 → 满标复审 → 还款中）等第一代不具备的能力。

## 新框架的工作方式

三层结构，自上而下单向调用，禁止反向依赖：

```
JSON 工作流   （用例：节点 + 连线，仅描述执行逻辑，不含业务代码）
   ↓
T-Blocks 层  （薄封装 + 注册表：将 JSON 中的节点名映射到具体函数）
   ↓
业务库 lib/   （10 个业务域的 Manager 类，封装页面操作与接口调用）
```

用例示例（登录边界测试，数据驱动，每行数据自动展开为一条独立用例）：

```json
{
  "id": "api/login_boundary_ddt",
  "data_rows": [
    {"row_id": "empty_password", "phone": "18800002008", "password": "", "expect_msg": "密码不能为空"},
    {"row_id": "user_not_exist",  "phone": "19900000000", "password": "Aa123456", "expect_msg": "用户不存在"}
  ],
  "nodes": [
    {"id": "login", "type": "step", "step_id": "step_account_login",
     "params": {"keywords": "${row.phone}", "password": "${row.password}"}},
    {"id": "check_msg", "type": "check", "check_id": "check_account_message_contains",
     "params": {"message": "${login.data.message}", "expected": "${row.expect_msg}"}}
  ],
  "edges": [{"source": "login", "target": "check_msg", "condition": "pass"}]
}
```

配套工具链（均为自研）：

| 工具        | 作用                                                      |
| --------- | ------------------------------------------------------- |
| pytest 插件 | 使 pytest 直接收集 JSON 工作流，并按目录自动打标记（`-m api` 即可筛选接口用例）     |
| 静态校验器     | 运行前检查 JSON：节点是否存在、参数是否齐全、变量引用与数据行字段是否完整                 |
| 调试器 CLI   | 无需执行完整流程，可单独调试某个节点或按指定顺序执行多个节点                          |
| 并发压测引擎    | 纯 Python 实现的压测能力（无需 JMeter）：多线程请求只读接口，统计成功率、响应时间分位数与吞吐量 |

## 实测发现的真实问题

以下问题均在对真实站点的测试中逐一排查确认：

1. **后端异常信息泄露**：列表接口传入 `page=0` 或 `-1` 时，服务器将 Java 错误堆栈原样返回
   （含数据库与 SQL 细节）。已固化为固定用例，服务端修复后可通过回归立即发现。
2. **投标隐性门槛**：标的显示「可投 5 万」，实际最低起投 1 万——投入 1000 元时页面无任何提示，
   且订单不生成。框架改为选标时自动读取并校验起投金额，不满足则自动换选下一候选标的。
3. **两段式投标确认**：点击「确认投标」后，真正下单的按钮位于弹窗内嵌的 iframe 中，
   常规点击无法完成提交；定位该问题后才真正跑通完整投标链路。
4. **满标复审接口失效（业务阻断级）**：复审接口 `loan/loan/reVerifySubmit` 对字段完整的
   合法请求固定返回 `{"status":100}`，弹窗不关闭、标的无法从满标待审流转至还款中
   （满标队列长期积压 400 余条无人可审，相互佐证）。通过 XHR Hook 抓取真实请求体与响应
   逐一排除了前端填写问题，确认为服务端缺陷，已固化为 BUSINESS\_LOAN\_002 基线用例持续监控。
5. **初审弹窗必填项无提示**：初审弹窗的「标签」字段为必填，但漏填时点击保存页面无任何
   错误提示、请求也不发出（前端静默拦截），易被误判为按钮失灵；与满标复审弹窗结构存在
   差异（多一个必填字段、单选项取值不同），框架通过弹窗结构探测后分别适配。
6. 其他已固化的问题：错误密码连续 3 次锁定账户、验证码须先获取再提交（会话级）、
   部分旧接口已下线返回 404 等。
7. **站内信前端细节瑕疵**：消息详情容器 CSS 类名拼写为 `sys-msg-detai`
   （应为 `sys-msg-detail`），且顶栏未读角标数字由接口异步渲染、进入消息页瞬间为空；
   框架读信链路按真实类名定位并对数字角标做轮询等待，保证状态断言稳定。

## 快速开始

```bash
pip install -r requirements.txt

# 离线自检（无需网络与浏览器）
python -m compileall -q lib tblocks
python tblocks/tblocks_debugger.py gate
pytest --tblocks-workflows tblocks/workflows/demo

# 冒烟（需测试站点可达，秒级）
pytest -m smoke

# 接口 / 性能 / 安全
pytest -m api
pytest -m performance
pytest -m security

# 一键回归（自动无头模式，日志输出至 output/）
.\scripts\run_regression.ps1 -Suite quick   # 冒烟+接口+性能+并发+安全
.\scripts\run_regression.ps1 -Suite all     # 全量
```

测试站点地址在 `.env` 中配置（参照 `.env.example`）。

## 测试报告

通过 `scripts/` 脚本运行时，每次执行自动产出三类报告（目录不存在会自动创建）：

| 报告 | 路径 | 用途 |
| --- | --- | --- |
| HTML 报告 | `output/reports/report_<套件>_<时间戳>.html` | 单文件自包含（CSS 内嵌），浏览器直接打开，可邮件/IM 发送，含每个用例耗时与失败堆栈 |
| JUnit XML | `output/reports/junit_<套件>_<时间戳>.xml` | 标准格式，供 GitHub Actions / Jenkins 等 CI 平台解析展示 |
| Allure 报告 | `output/allure/report/index.html` | 运行结束检测到本机装有 allure CLI 时自动 `allure generate`；未安装则跳过（原始结果始终由 pytest.ini 的 `--alluredir` 写入 `output/allure/results`，装好 CLI 后可随时手动生成） |

另外，引擎为每个工作流留有逐步执行明细：`output/atomic/<时间戳>_<工作流ID>/`
下的 `result.json` 与 `summary.md`；控制台完整输出同时落盘为
`output/regression_<套件>_<时间戳>.log`。

直接用 pytest 命令运行时，追加 `--html=output/reports/report.html
--self-contained-html --junitxml=output/reports/junit.xml` 可获得同样的报告产物。

```bash
# 可临时选择 all 全量（Linux 无头 Chrome，约 1.5~2.5 小时，首次运行需观察适配）。
# 凭据默认走代码内教学站配置；可在仓库 Settings -> Secrets 用同名变量覆盖
# （BASE_URL/BACK_URL/ADMIN_USERNAME/ADMIN_PASSWORD/TEST_USER/TEST_PASSWORD 等）。

# 本机任务计划管理（PowerShell）
.\scripts\install_nightly_task.ps1                 # 注册：每天 02:00 全量
.\scripts\install_nightly_task.ps1 -Time 23:30    # 改时间
.\scripts\install_nightly_task.ps1 -Suite quick    # 改为快速套件
Start-ScheduledTask -TaskName 'TBlocks Nightly Regression'  # 立即试跑
.\scripts\install_nightly_task.ps1 -Unregister     # 卸载
```

注意：GitHub 定时任务以 UTC 计时且整点高峰可能延迟；本机任务计划准点执行，
但凌晨 02:00 需保持开机、联网与登录状态（错过后开机自动补跑一次）。

## 目录结构

```
├── lib/                # 业务库：10 个业务域（会员/资金/理财/后台/接口/探针/压测…）
│   └── common/<域>/    #   每个域一个 Manager 类 + 步骤/检查入口函数
├── tblocks/
│   ├── step_impl/      # 117 个步骤节点的薄封装
│   ├── check_impl/     # 77 个检查节点的薄封装
│   ├── workflows/      # 55 个 JSON 工作流（smoke/api/ui/business/backend 等 14 个目录）
│   └── utils/          # 引擎：执行器 / 变量解析 / pytest 插件 / 静态校验
├── scripts/            # 一键冒烟、一键回归脚本
└── old_framework/      # 第一代 PageObject 项目（独立可运行）
```

## 关于 old\_framework/

第一代工程完整保留，与新框架零依赖、零共享，用于对照两代方案的差异：

```bash
cd old_framework
pip install -r requirements.txt
pytest scripts/ --collect-only   # 收集 169 个用例
python tools/run_tests.py --all
```
